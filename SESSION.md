## Pending issues

- Stack overflow on the heaviest generated nixpkgs files: `pkgs/development/haskell-modules/hackage-packages.nix` (~662k exprs) crashes consistently during `run_inference` → canonicalization → file-sig phase, and `pkgs/development/lisp-modules/imported.nix` (~153k exprs) crashes after the `EquivDsu`/`constrain_equal` equivalence patch (`7f241f9`) — it succeeded pre-patch. The canonicalize path is already `stacker::maybe_grow`-guarded, so either a non-canonicalize code path (e.g. deferred overload resolution, simplify, or narrow analysis) is recursing unguarded, or the equivalence-class collapse creates deeper component chains in file-sig Pass 2 than the pre-patch path. Reproduce via `nixpkgs-test` (no args; crashes on `imported.nix`). `nixpkgs-test lib/ nixos/` (2494 files) is clean on both sides of the patch — same 74 errors, 38 warnings, same file set. Prioritize if users hit this on real files; otherwise stacker-grow the suspected site once located.
- Doc comment annotations on let bindings (e.g. `/** type: f :: BwrapParams -> string */`) don't fully expand type alias internals into inference. The `f` gets the correct outer structure (param and return types) but nested alias content like `[BwrapArg]` remains a type variable in the element position. Using `val` declarations in stubs works correctly because the type is resolved fully by the alias registry. This limits expected-type completion for locally-defined functions — it only works well when function types come from stubs (`val` declarations) or from inference (body usage constraining the parameter type).
- `cursor_is_in_attrset_value` can't detect value position when the value expression is missing (parse error), e.g. `f { name =  ; }` — rnix's `AttrpathValue::value()` returns None. Callsite completion fires incorrectly in this edge case.

- Regenerating `stubs/lib.tix` via `gen_lib_stubs.py` produces some invalid type signatures from newer noogle data (e.g. `{ [string] : a }`, pipe's pseudo-syntax). Needs manual overrides added for `attrVals`, `attrValues`, and other newly-broken signatures before regenerating. The `@source` emission code in `gen_lib_stubs.py` is correct and tested, but the stubs aren't regenerated yet due to these unrelated noogle data regressions.
- When `set_builtin_stubs_dir` is called multiple times with different directories, module aliases (e.g. `Pkgs`) from the old directory persist in `self.aliases` because `load_declarations` merges modules. This is harmless in practice (the LSP only calls `set_builtin_stubs_dir` once), but could cause stale fields to accumulate if the method were called repeatedly with different dirs.
- Un-narrowed refs to params with non-null defaults (e.g. `? 0`, `? false`) show only the default type in hover rather than the full type. The hover fallback now only triggers for `TyVar` and `Primitive(Null)`, so `? 0` defaults would show `int` instead of the full parameter type. Low-priority since `? null` is the dominant pattern.
- `constrain.rs:431-443`: Over-conservative intersection constraining when both sides have type variables. The `_ =>` fallback constrains each member individually, skipping disjointness checks. Needs DNF decomposition for correctness (existing TODO in code).
- `group_def` (SCC grouping) skips non-recursive attrset bindings — `NameDependencies::traverse_expr` calls `bindings.walk_child_exprs()` instead of `traverse_bindings()` for non-rec attrsets. This means `build_name_to_import` (which depends on `group_def`) misses re-export bindings like `{ foo = import ./real.nix; }`. The new `import_nav::resolve_field_transitively` works around this by using `module_indices.binding_expr` directly, but other code paths relying on `build_name_to_import` for non-rec attrsets may have the same gap.
- Cross-file find-all-references only covers open/analyzed files (those in the DashMap snapshots). Files that import the target but haven't been opened won't appear in results. Could be enhanced with demand-driven analysis via `LspSyntaxProvider`.
- NixOS/HM config stubs use `type NixosConfig = { ... }` rather than `module`. This is correct (deeply nested options don't map to module syntax), but users who want precise types for custom NixOS options have no good extension path. Consider a type-level extension syntax (e.g. `type NixosConfig = NixosConfig & { myModule: { enable: bool, ... } }` or an `extend type` form) so users can augment the generated config types without replacing them entirely.
- Pre-existing clippy warnings on main (not in changed code): `crates/lsp/src/state.rs:1151/1158/1210` (cloned_ref_to_slice_refs) and `crates/cli/src/init.rs:1510+` (fmt formatting drift). Unrelated to context-improvements work.
- Integration tests under `crates/cli/tests/` duplicate helper functions across files (`repo_root`, `tix_cli`, `assert_binding`, `nixpkgs_src`). Currently duplicated in `env_stubs.rs`, `nixpkgs_lib.rs`, and the new `custom_stubs.rs`. Should be extracted to a shared test-support module (e.g. `crates/cli/tests/common/mod.rs`, following the LSP e2e test pattern at `crates/lsp/tests/common/`) once a third consumer lands.
- Generated `nixos.tix` inlines the full top-level NixOS option tree ~8× because the NixOS schema has recursive self-embeddings: `specialisation.<name>.configuration`, `system.build.vmVariant`, `vmVariantWithBootLoader`, container `config`, etc. Each declares its type as a full NixOS submodule, so the extractor walks the whole tree again at that position. Baseline `nixos.tix` is ~148k lines; adding user modules (e.g. `myOptions`, `age`, `home-manager`) at top level multiplies through all 8 embeddings. Fix: teach the stub printer to emit `: NixosConfig` (self-reference) when a nested submodule's shape matches the top-level alias, either by identity from the extractor or by structural equality in the Rust writer. Expected ~8× file-size reduction, faster LSP startup.
